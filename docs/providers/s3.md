# The `s3` provider

Topics as Avro files in an Amazon S3 bucket. Artifact `rawdata-client-provider-s3`, module
`io.descoped.rawdata.provider.s3`. It is the [`filesystem`](filesystem.md) engine on a bucket: the same segments,
layout and order as [`gcs`](gcs.md). It uses the AWS SDK for Java 2, with the SDK's JDK-based HTTP client (no
Apache, Netty or CRT), so the SDK's credentials and region handling work as in any AWS application.

## Configuration

| Key | Default | |
|---|---|---|
| `rawdata.client.provider` | | `s3` |
| `s3.bucket-name` | | required |
| `s3.prefix` | none | a folder in the bucket for the topics, for example `rawdata/` |
| `s3.region` | the SDK's region chain | the bucket's region, for example `eu-north-1` |
| `s3.credentials` | `default` | `default`, `profile`, `static` or `anonymous` |
| `s3.profile` | | the profile in `~/.aws/config` and `~/.aws/credentials`, for `profile` |
| `s3.access-key-id`, `s3.secret-access-key` | | for `static`, for example an emulator's |
| `s3.endpoint` | AWS's | another endpoint, for an S3-compatible store or an emulator |
| `s3.path-style-access` | `true` for a bucket name with dots, else `false` | path-style requests (`https://host/bucket/key`) |
| `s3.sse` | the bucket's default encryption | `AES256` or `aws:kms`, asked for on every put |
| `s3.sse-kms-key-id` | the account's default key | the KMS key, for `aws:kms` |
| `s3.poll-interval-ms` | `1000` | how often a waiting consumer looks for new messages |

### Credentials and region

`default` is the SDK's default credentials chain:
1. environment variables (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN`);
2. Java system properties (`aws.accessKeyId`, …);
3. web identity (EKS IRSA, or another OIDC provider: `AWS_WEB_IDENTITY_TOKEN_FILE` and `AWS_ROLE_ARN`);
4. the profile in `AWS_PROFILE` (or `default`) from `~/.aws/credentials` and `~/.aws/config`, including SSO and role
   profiles;
5. container credentials (ECS, EKS Pod Identity);
6. the EC2 instance metadata service (IMDSv2).

The STS, SSO and SSO OIDC modules come with the provider, so web identity and SSO profiles work without adding
anything. Without `s3.region`, the SDK's region chain decides: `AWS_REGION`, the profile's `region`, then the instance
metadata.

The account needs `s3:ListBucket` on the bucket (for the prefix), and `s3:GetObject`, `s3:PutObject` and
`s3:DeleteObject` on the objects under the prefix. With a customer KMS key it also needs `kms:Encrypt`, `kms:Decrypt`
and `kms:GenerateDataKey` on that key.

### Bucket names with dots

Virtual-hosted HTTPS (`https://my.bucket.s3.amazonaws.com`) does not work for a bucket name with dots: the
certificate covers one level below `s3.amazonaws.com`. The provider uses path-style requests for such names unless
`s3.path-style-access` says otherwise.

## Objects

```
s3://<bucket>/<prefix><topic>/segments/0000000000000000000.avro
s3://<bucket>/<prefix><topic>/metadata/k<hex of the key>
```

A segment is put in one request with `If-None-Match: *`, so S3 creates it only if no object has its key. If the key
is taken (412), the store reads the object back: its own bytes mean a retry after a lost response, and the segment
counts as created; other bytes mean another process wrote the topic, and the publish throws
`RawdataWriterConflictException` (see [one writer per topic](../contract.md#one-writer-per-topic)). When S3 answers
409 (another conditional put on the key was in flight), the store waits a little (50 ms, doubling up to 1 s, with
jitter) and asks again, up to ten times. Metadata entries are plain puts: S3 applies them atomically, and the last
write wins. A metadata key is at most (1024 − the prefix, topic and `/metadata/k`) / 2 bytes, about 500.

A HEAD response has no body, so S3 answers a missing object and a missing bucket with the same 404. The first time a
client sees one, it lists the prefix once (the `s3:ListBucket` permission it needs anyway), so a wrong bucket name
fails with `NoSuchBucket` instead of looking like an empty topic.

The SDK retries throttling, 5xx and I/O errors, six attempts per request as in `gcs`, and sends checksums as it does
by default.

Messages are visible and durable when `publish` returns, one object per publish: publish in batches where you can.

## Dependencies and the module path

The provider depends on the Avro engine and the AWS SDK's `s3`, `url-connection-client`, `sts`, `sso` and `ssooidc`
modules and what they bring: about 30 SDK jars. The SDK's other HTTP clients are excluded, and banned by the
enforcer. The SDK's jars are automatic modules with stable names, so the provider runs on the module path or the
class path.

## Tests

- The shared contract (`RawdataClientContractTest`) and the store contract (`AvroStoreContractTest`) run against
  [S3Mock](https://github.com/adobe/S3Mock) (`adobe/s3mock`) in Docker, plus the provider's own tests (the object
  layout, encryption, configuration, a 409 from a stub).
- **Live tests** run the same contract against real S3. They run only when asked:
  ```sh
  AWS_PROFILE=<profile> ./mvnw verify -pl rawdata-client-provider-s3 -am -Drawdata.s3.live=true
  ```
  The bucket and region default to the project's test bucket (`-Drawdata.s3.live.bucket`, `-Drawdata.s3.live.region`
  to change them). A run writes under `rawdata-client-test/<random>/` and removes it afterwards. CI does not run
  them.
- S3Mock does not apply `If-None-Match` atomically when two puts race; that does not matter for one writer per topic,
  and the contract's second-writer test is sequential.
